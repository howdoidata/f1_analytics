### Pattern divergence

The findings below were each **verified empirically** by the analysis agent driving the two code paths with stubbed inputs — not inferred from reading.

**F8 — Two orchestrator hardenings landed in the later script only, and the earlier one still crashes the whole run. (CONFIRMED, highest-severity code finding.)**
`run_fetch_subprocess` exists twice: `pull_fastf1_data.py:76-130` (Story 1.6) and `build_combined_dataset.py:155-219` (Story 1.7, whose docstring says it "Mirrors `pull_fastf1_data.run_fetch_subprocess`"). The later copy hardened three things the earlier one never received:
1. **Non-dict JSON guard.** `build_combined_dataset.py:202-206` adds `if not isinstance(result, dict): result = {}`. `pull_fastf1_data.py:118-123` has the `JSONDecodeError` handler but no `isinstance` guard. Driving both with a stubbed subprocess returning `'["a","b"]'`: `pull_fastf1_data` raised **`AttributeError: 'list' object has no attribute 'get'`**; `build_combined_dataset` returned a clean statused failure.
2. **`mkdir` failure.** `pull_fastf1_data.py:82-83` calls both `mkdir`s *outside* the `try` (which opens at `:105`) under a narrow `except OSError` at `:115`. `build_combined_dataset.py:184-185` moved them inside a broad `except Exception`, with a comment naming the intent. Pointing both at a cache path blocked by a regular file: `pull_fastf1_data` raised an uncaught **`NotADirectoryError`**; `build_combined_dataset` returned a statused failure.
3. **`"empty"` treated as success.** `build_combined_dataset.py:212` gates on `status not in ("pass","empty")`; `pull_fastf1_data.py:123` gates on `!= "pass"`, so a legitimate `status: "empty"` from `fastf1_fetch.py:174` is overwritten into `failed` with a synthesized exception string — partly compensated by a *second* helper (`_fetch_failure_detail`, `:160-171`) that exists only because the first copy clobbers the field.
**Consequence:** both crash paths defeat the AD-13 per-race isolation guarantee that `pull_race` (`:174`) exists to provide — one race's disk-full or garbled-worker error takes down all five races instead of failing that race and continuing. This is the epic's clearest story-seam defect: Story 1.7 learned the lesson and Story 1.6's code never got it back.

**F9 — Advisory validation runs in two of three build scripts; the curated Kaggle baseline is never validated when it is built. (CONFIRMED.)**
`pull_fastf1_data.py:275-278` and `build_combined_dataset.py:457-460` both call the shared `load_present_tables`/`run_validations`/`log_validation_results`/`print_validation_findings` quartet. `scripts/build_f1_dataset.py` imports nothing from `f1_analytics.validation` and logs no `source_load` row, despite `"kaggle"` being a registered source (`validation/store.py:21`). ### Diff-scope review (adversarial / edge-case / verification-gap lenses)

Run via `bmad-review` over the full product tree. The agent noted the same missing `project-context.md` and continued without it. Every finding below was verified by executing the code path; **F19 was additionally reproduced independently by me** before being recorded.

**F19 — A season with exactly one round crashes the shared standings function, after partial writes. (CONFIRMED — most severe finding of the epic.)**
`src/f1_analytics/data_sources/standings.py:24-29`, `add_standing_rank`. The `groupby(group_columns).apply(...)` returns a **DataFrame instead of a Series when there is exactly one group**, so the assignment at `:29` raises `ValueError: Cannot set a DataFrame with multiple columns to the single column standing_rank`.

Reproduced independently, twice — first against the helper, then through the real production entry point `compute_cumulative_standings(results, 'driver_id', 'driver_name')`:
```
season with 1 round(s): RAISED ValueError: Cannot set a DataFrame with multiple columns
                               to the single column standing_rank
season with 2 round(s): OK -> 4 standings rows
```
`compute_cumulative_standings` calls `add_standing_rank(grouped, ["season","round"], [id_column])` — so **one season/round is one group**, and this is the single function all four standings call sites share.

**Why the seam caused it, in the code's own words.** Story 1.7's session *hit this exact error* and misdiagnosed it as empty-frame-only. The evidence is its own comment at `scripts/build_combined_dataset.py:323-334`, which names the identical `ValueError` verbatim and records that "that raise landed AFTER `raw_jolpica_results` and `combined_results` were already written, leaving the two standings tables missing — the partial-write-then-crash class this script's fail-fast discipline exists to prevent." The guard it then added at `:335` is `if combined_results.empty:` — **too narrow: the trigger is one group, not zero rows.** Story 1.5's session never saw the failure, so `kaggle_csv.py:103` is unguarded too.

**Two reachable production scenarios:**
1. *Story 1.7 path* — the **first race weekend of a season**. Curated `results` holds exactly one `(season, round)` and Jolpica returns `empty`. `main()` crashes with `combined_results`, `raw_jolpica_results`, and the coverage view **written**, and both `combined_*_standings_by_round` tables **missing** — exactly the partial state the docstring set out to prevent.
2. *Story 1.5 path* — `scripts/build_f1_dataset.py` via `kaggle_csv.build_curated_tables:103`; a single-round CSV extract crashes before any write.

**Why no test catches it:** `tests/test_standings.py:16-24` uses a 3-group fixture (2024 rounds 1-2 plus 2025 round 1); `tests/test_build_combined_dataset.py` fixtures use 5 rounds. No fixture on either side has fewer than 3 groups, so the boundary is invisible to all 155 tests. Live data does not hit it because the historical dataset has many rounds per season — this is a **new-season** failure.
**Fix direction:** guard inside `add_standing_rank` itself so both stories inherit it, not at one caller. Adding a 1-group case to `tests/test_standings.py` closes both call sites at once.

**F20 — Empty standings tables land with every column typed `INTEGER`, including the string columns. (CONFIRMED.)**
`scripts/build_combined_dataset.py:335-339` returns `pd.DataFrame(columns=[...])` with no dtypes — all `object` — and DuckDB infers `INTEGER` for every column, including `driver_id`, `driver_name`, `race_name`, and `source`, all of which are `VARCHAR` in a populated build. The comment at `:110-112` states the intent that "a degenerate build still writes tables with the same schema a populated one produces." It does not.
**Consequence:** an Epic 2 consumer binding a string predicate against `combined_driver_standings_by_round.driver_id` gets a DuckDB type error after a pre-season run and works after the first race — an intermittent failure tied to build ordering. `tests/test_build_combined_dataset.py:713-717` asserts only `COUNT(*) == 0`, never the schema. Compounds F18.

**F21 — `validate_ids` degrades a whole season's gap-fill to empty on a malformed curated table. (CONFIRMED code path.)**
`src/f1_analytics/data_sources/jolpica_loader.py:250` — `set(drivers["driver_id"])` raises a bare `KeyError` if curated `drivers` lacks the column. It is caught and wrapped at `:286`, so it degrades rather than crashing — but it degrades **the entire season's gap-fill to empty while printing a fetch-style message**, the same silent-data-loss shape the `points`-cast post-mortem at `:158-167` documents.
**Why the seam:** Story 1.7 added `require_races_columns` for column-level checking but applied it only to `races`, not to `drivers`/`constructors`, which this loader indexes by name.

**F22 — `refuse_regression` compares only row counts. (CONFIRMED design limitation.)**
`src/f1_analytics/database/duckdb_io.py:60-66` accepts an equal-count write of entirely different content — verified: 5 rows `[1,2,3,4,5]` replaced by `[9,9,9,9,9]`. `tests/test_duckdb_io.py:73` asserts this as intended. Flagged because `build_combined_dataset.py:434` branches on `status == "failed"` to decide stale-data honesty, so a *corrupt-yet-same-length* fetch bypasses the guard entirely. Documenting the guard as count-only would stop a future story over-trusting it.

### Fixed during this retrospective

**F19 — FIXED.** `src/f1_analytics/data_sources/standings.py:24-48`, with regression tests at `tests/test_standings.py`.

The root cause was narrower than first diagnosed and worth recording precisely: `groupby(...).apply(...)` returns a **Series** for two or more groups but pandas **unstacks it into a DataFrame when there is exactly one group** — verified directly:
```
rounds=1: DataFrame shape=(1, 2) index.nlevels=2
rounds=2: Series    shape=(4,)   index.nlevels=3
rounds=3: Series    shape=(6,)   index.nlevels=3
```
(An initial `group_keys=False` attempt did **not** fix it — recorded because the obvious remedy is a dead end.) The fix replaces the `apply` with a vectorized, shape-stable computation, so both call sites inherit it rather than one caller being patched.

**F23 — a second, previously-invisible defect, found only because F19's fix exposed it. (CONFIRMED, fixed.)**
After the first fix the combined tables came out **0-based** while the curated tables were 1-based. Cause: rank is derived from each row differing from the row above it, so the **frame's very first row has no predecessor** — deriving "first row of a group" from `group_columns.shift()` made that row compare against NaN, `.ne()` answered `False` on both comparisons, and it started no rank at all. Reproduced live as **1950 round 1 — the first race in the dataset — ranking Nino Farina 0** while all 1,159 other rounds ranked their leader 1. Fixed by deriving the group's first row from a group-wise `cumcount()` instead.

**Why this is a story-seam finding:** the curated path (Story 1.5) and the combined path (Story 1.7) call the *same* shared function, and the two disagreed on rank base without either session noticing — `driver_standings_by_round` min=1, `combined_driver_standings_by_round` min=0. Nothing tested the rank base, and no consumer existed yet to trip over it. Epic 2/3 scoring reads these standings.

**Verification that the fix changes nothing else.** Old and new implementations were run against the identical inputs and compared:
- Direct comparison of the two implementations over the full combined data: **`driver: identical = True`, `constructor: identical = True`** (26,026 and 12,861 rows).
- After a full rebuild of both scripts, every curated table is unchanged: `driver_standings_by_round`, `constructor_standings_by_round`, `final_driver_standings`, `results`, `combined_results` all report **0 before-only rows**.
- The combined tables' only change is the rank base: the distribution of `after.standing_rank - before.standing_rank` is **`delta=1` for all 26,026 rows**, and **0 rows differ on any non-rank column**.
- All four standings tables now report `min=1`; **0 rank-0 rows remain**.
- Test suite: **155 → 157 passing** (two regression tests added, each confirmed red before the fix).

Tie semantics are preserved — a single-round tie still yields ranks `[1, 1]`.

**Note:** `data/processed/f1_analytics.duckdb` is gitignored and was rebuilt in place during this retro. The stale 0-based ranks are gone; anything that read those tables before 2026-08-20 read 0-based combined ranks.

### Process lessons — what would prevent the next one

- **A fix found at a story seam must be pushed back across the seam.** F8 and F19 are the same failure mode: a later story diagnosed a real defect, fixed its own copy, and left the earlier story's copy broken. F19 is worse because the later session *wrote the ValueError verbatim into a comment* and still guarded only its own narrower case. **Lesson:** when a story fixes a defect in code it copied or shares, closing it should require checking the origin.
- **Deferring under a spec token budget silently narrows the acceptance bar.** F1's ACs were dropped from the story spec for size, and the story then closed green against the narrowed spec while `epics.md` still declared them. **Lesson:** a split that removes an AC should either amend the epic spec in the same commit or block the story's `done`.
- **Test fixtures that never probe a boundary hide it from all lenses.** No standings fixture had fewer than 3 groups, so 155 tests, three review lenses, and two live builds all missed F19. **Lesson:** for any grouped or windowed computation, fixture the degenerate cases — one group, one row, first row.
- **Deliberate duplication needs a binding assertion.** The epic already does this well once (`KNOWN_COVERAGE_STATUSES` raises on SQL/Python drift, F13) and not at all for the retry constants or the empty-standings schema mirror. **Lesson:** where duplication is unavoidable, add the cross-check.
- **Commit subjects should carry the story key.** F5 — no automation can attribute this epic's commits to its stories.
